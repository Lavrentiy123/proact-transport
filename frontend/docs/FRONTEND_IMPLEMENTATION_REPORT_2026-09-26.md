Пример риска: для `sample_id=131672_1767670500` момент `T=03:35`, целевая остановка `53700172828`, план `03:50`; расписания train/test содержат факт `03:51:18` (+78 с). Для этого борта в validate-телеметрии 466 строк до/в `T` и 5523 строки после `T`. Текущий frontend CSV не импортирует, поэтому прямой утечки в демо сейчас нет. Актуальное описание колонок — `data/DATASET_README.md`; `data/README_DATASET.md` содержит старые предположения.

В `contracts/schemas.py` `VehicleState.lat/lon` — обязательные `float`, но географический диапазон не ограничен. Поэтому кадр с `lat=95` принимается как контрактный, запись остаётся в количестве полученных бортов, а карта не ставит маркер и объясняет разницу. `lat:null` или отсутствующий `lat` делают кадр невалидным. Координата `(0,0)` численно допустима, но скрывается текущей продуктовой политикой. Время в контракте — ISO-8601 без зоны; дробные секунды встречаются в данных и должны поддерживаться фронтендом.

Воспроизведение ключевых проверок:

```powershell
Get-FileHash data/test/traffic.csv, data/validate/traffic.csv -Algorithm SHA256
Get-FileHash contracts/examples/ws_snapshot.json, frontend/src/data/snapshot.json -Algorithm SHA256
$p = (Import-Csv data/validate/points.csv)[0]
$rows = Import-Csv data/validate/traffic.csv | Where-Object tr_id -eq $p.tr_id
@($rows | Where-Object { $_.event_time -le $p.T }).Count
@($rows | Where-Object { $_.event_time -gt $p.T }).Count
```

## Решение по интерфейсу и наблюдения

Экран организован как источник/связь и время → состояние парка → рабочая зона из ленты, карты и карточки → диаграмма. На desktop карта занимает центральную колонку, а длинные лента и карточка прокручиваются внутри своих панелей. На узком экране секции идут последовательно, без горизонтальной прокрутки. Тёмная географическая подложка сохранена; резервная схема подписана как отдельное состояние. Палитра поверхностей и границ ограничена, красный/жёлтый/зелёный зарезервированы для риска; текст и форма дополняют цвет. Поиск и фильтры расположены непосредственно над лентой; число бортов из потока и число допустимых позиций подписаны раздельно. Это наше проектное решение, **не результат исследования с реальными диспетчерами**.

Опорные идеи сверены с [IBM Design Language](https://www.ibm.com/design/language/data-visualization/design/basics/) (обзор, затем выбор и детали; ясные подписи), [Carbon](https://carbondesignsystem.com/components/data-table/usage/) (поиск рядом со списком), [GOV.UK Design System](https://design-system.service.gov.uk/components/tag/) (статус текстом, а не только цветом), [W3C Focus Visible](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible) и [OpenFreeMap](https://openfreemap.org/) (атрибуция). Ссылки являются источниками принципов, а не шаблонами макета.

Исходный browser осмотр в Codex IAB 26.09 показал тёмную карту и три демо-борта, но горизонтальную прокрутку при 320 px (`clientWidth=305`, `scrollWidth=320`). Финальная production-сборка 27.09 дала равные `scrollWidth` и `clientWidth`: 305/305 на 320 px, 360/360 на 375 px, 795/795 на 810 px, 1351/1351 на 1366 px и 1905/1905 на 1920 px. На 1000 синтетических бортах карта имеет высоту 679 px и видимые кластеры. При 375×812 и 100 алертах лента перед картой длинная; в её нижней части добавлена ссылка «К карте». Снимки проверялись визуально в IAB, отдельные файлы снимков в репозитории не сохранялись.

Расчёт контраста для выбранных текущих CSS-токенов (sRGB/WCAG, без учёта прозрачных наложений): основной текст `#eaf3f7` на фоне `#0b141c` — 16,50:1, приглушённый `#91a6b2` — 7,34:1, вторичный `#a7bdc7` на панели `#14212c` — 8,37:1, красная задержка `#ff8b89` на `#1b2b36` — 6,44:1, фокус `#86d5e7` на `#0b141c` — 11,22:1. Это адресная проверка пар цветов; она не заменяет проход всех состояний, оверлеев и увеличения текста.

## Матрица исполнения

Промежуточные повторные прогоны после первой серии исправлений: `npm run test:contracts` — PASS, 19 адресных проверок на Vite SSR; `npm run build` — PASS. Стартовый JS chunk уменьшился с 1286,95 КБ (gzip 359,78 КБ) до 268,58 КБ (gzip 84,57 КБ); карта вынесена в chunk 1033,76 КБ (gzip 279,89 КБ), worker 509,70 КБ. Предупреждение Vite о большом chunk остаётся. Это измерение размера файлов, а не доказательство ускорения времени до интерактивности. Production-экран после reload отдал демо, лениво загрузил тёмную карту и видимую атрибуцию; консоль показала только внешнее предупреждение стиля OpenFreeMap `wood-pattern`.

Промежуточная нагрузка на **dev-сервере** в Codex IAB при 1366×900 со stub `STUB_VEHICLES=N`: для 100 бортов первое появление счётчика заняло 228 мс, для 500 — 200 мс, для 1000 — 255 мс. Замер включает вызов браузерного select и ожидание видимого текста через CUA, поэтому это верхняя оценка времени доступности счётчика, а не замер полной отрисовки WebGL. При 500 учтено 475 допустимых маркеров, при 1000 — 950; остальные имеют преднамеренный `lat=95`. Горизонтальной прокрутки на 1366 px нет. После устранения ложного WebGL fallback тёмная карта и кластеры видны на 500/1000. Первоначально кластеры уходили ниже первого экрана: CSS grid растягивал карту до 1361,5 px. После исправления высота карты составила 679 px (верх 205, низ 884) при 1366×900, а кластеры видны в рабочей области; старт live показывает обзор без автоматического выбора борта.

Повтор на **production Docker-сборке** 27.09 с nginx и синтетическим WS-потоком 1 Гц: 100/500/1000 записей корректно отображаются в верхнем счётчике; карта показывает соответственно 95/475/950 допустимых позиций и объясняет 5/25/50 скрытых; группы риска видны при 500 и 1000, кадры продолжают поступать без наблюдаемого зависания. При 500 выбран борт `200000` из алерта: карточка и маркер согласованы, REST 404 маршрута показан отдельной полосой и не удалил прогноз. При 1000 выбранный борт и лента остаются рабочими. Повторный production-замер от переключения demo → live до появления числа в DOM составил 141 мс для 100, 186 мс для 500 и 176/189 мс для 1000. Каждый замер включает UI-действие, WS-подключение и ожидание текста, но не подтверждает завершение WebGL-отрисовки или частоту кадров. Это ручная оценка в Codex IAB на Windows, не профилирование памяти. Синтетический stub не подтверждает ожидаемое число реальных бортов.

Финальное окружение: Windows, Node.js 24.16.0, npm 11.13, Docker Engine 29.5.3, Codex IAB; даты прогонов — 26–27.09.2026. ## Внешние блокеры и условия продолжения

**FE-08:** в текущем checkout нет исполняемого сервиса backend. При его появлении нужно подключить контейнер frontend к сети с адресом `backend:8000`, получить фактический WS-снимок, сверить количество `vehicles` с UI и допустимыми позициями, проверить борт с алертом и без него, REST-трек, пустой/частичный кадр и восстановление после обрыва. Отдельно подтвердить семантику `vehicles` как полного снимка, отсутствие/`null`/`[]`, завершение рейса и координаты при невалидном GPS. До такой проверки нельзя утверждать мониторинг всего транспорта Москвы.

**FE-20:** нет действующего `POST /api/v1/actions` и договора об идемпотентности, статусах и истории решения. На текущем экране рекомендация только показана диспетчеру. Отправку водителю не имитировать.

**Оставшиеся проверки качества:** реальный 200% масштаб текста и экранный диктор, браузер без WebGL (выполнена только принудительная list-mode сборка), browser-инъекции REST 500/тайм-аута и повреждённого JSON, замер WebGL fps/памяти и запуск GitHub Actions после разрешённого push. Эти пункты отмечены PARTIAL в матрицах; их нельзя считать пройденными из-за зелёного build.
