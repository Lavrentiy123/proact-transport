# ПроАкт.Транспорт — frontend

React + TypeScript диспетчерская для прогнозов отклонений транспорта. По умолчанию открывается **живой поток** backend (WebSocket `/ws/live` + REST); автономный демо-сценарий без backend — `?source=demo` или переключатель «Источник». Картографическая подложка загружается из OpenFreeMap; если сеть или сервис недоступны, остаётся схема маршрута без подложки.

## Локальный запуск

Требуется Node.js 24 и npm.

```bash
cd frontend
npm ci
npm run dev
```

Открыть `http://localhost:5173`. Проверки: `npm run typecheck`, `npm run test:contracts` и `npm run build`. Контрактный smoke проверяет повреждённые и частичные кадры, порядок времени, отсечение будущих точек маршрута и форматирование задержки. Тот же набор запускается в [CI](../.github/workflows/frontend.yml).

## Управление демо (`http://localhost:5173/?source=demo`)

- **Источник → Демо-сценарий**: контрактный снимок и синтетические маршруты. `×5` означает 5 секунд модельного времени за 1 секунду просмотра.
- **Пауза / Продолжить** останавливает и возобновляет шкалу; **Начать заново** возвращает её к 12:40:00.
- Через 45 модельных секунд появляется второе предупреждение. Борта перемещаются по синтетическому маршруту.
- Сценарии **Пик алертов**, **Нет данных**, **Потеря связи** проверяют крайние состояния.
- Нажмите на предупреждение или маркер борта, чтобы сменить маршрут, карточку и диаграмму. Поиск и фильтры ленты не меняют общий счётчик алертов; кнопка «Показать все» открывает события после седьмого.
- Карта сначала показывает все борта текущего снимка. Кнопка **К маршруту** приближает выбранный маршрут; **Все борта** возвращает обзор.

## Живой поток

Режим по умолчанию. Frontend подключается к `WS /ws/live`, раз в 15 с обновляет трек выбранного борта (`GET /api/v1/tracks/{tr_id}`), раз в минуту — сеть маршрутов до 60 бортов (цвет по риску, не больше 6 запросов одновременно), раз в 10 с — панель горизонта (`GET /api/v1/metrics/horizon`: доля прогнозов за 10–15 мин и онлайн-ошибка). Кнопки карточки «Отправить водителю» / «Отклонить» вызывают `POST /api/v1/actions` (тайм-аут 8 с) и показывают ответ водителя. Жёлтая плашка «ДЕГРАДАЦИЯ» и баннер — режим `DEGRADED` (обрыв потока); недоступное ML-ядро показывается отдельным баннером. Перемотка времени replay вперёд больше чем на 5 минут тоже начинает новый сеанс: backend сбрасывает предупреждения. При обрыве WebSocket повторяет подключение с паузой 1–10 секунд, оставляя последний снимок с предупреждением об устаревании. Перемотка времени replay назад больше чем на 60 с (`--loop`, `POST /api/v1/replay/control`) начинает новый сеанс без переподключения. До первого снимка видно ожидание данных; раздел «Диагностика» показывает состояние WS, время последнего снимка, возраст пакета и доступность ML-ядра. Некорректные кадры игнорируются; `status.sim_time` может опережать время кадра на 2 с реального времени (при ×10 — на 20 с модельного): backend вычисляет статус после бортов на идущих часах. Отдельный прогноз или предупреждение с меткой позже кадра отбрасывается без потери всего кадра.

Vite в разработке проксирует `/api` и `/ws` на `localhost:8000`. В контейнере nginx проксирует те же пути на `backend:8000` и слушает порт **3000** по `contracts/README.md`.

Для локальной проверки живого режима без команды backend во втором терминале запустите `npm run dev:stub`. Это тестовый WebSocket/REST поток на порту 8000 (включая `POST /api/v1/actions` и `GET /api/v1/metrics/horizon`); не запускайте его одновременно с настоящим backend.

Для нагрузочной проверки stub принимает переменные `STUB_VEHICLES=0|1|3|100|500|1000` и `STUB_ALERTS=0..1000`. Например, в PowerShell перед `npm run dev:stub`:

```powershell
$env:STUB_VEHICLES = '500'
$env:STUB_ALERTS = '50'
npm run dev:stub
```

Такие борта синтетические; каждая 20-я позиция при 100+ бортах специально имеет недопустимую широту для проверки счётчиков.

Для адресных browser-проверок задайте `STUB_CASE` перед запуском stub. Без него поток остаётся обычным. Новый клиент сразу получает актуальный снимок, затем один кадр каждую секунду. Модельные часы общие для процесса и на каждом тике сдвигаются на 5 секунд; номер тика для инъекции считается **для каждого подключения** отдельно.

| `STUB_CASE` | Инъекция и ожидаемый момент |
| --- | --- |
| `bad-frame` (N04) | На 3-м тике один повреждённый JSON вместо снимка; 1-й, 2-й и 4-й тики валидны. |
| `track-race` (N05) | `GET /tracks/131672` задержан на 3500 мс, другие маршруты доступны сразу. Выберите борт 131672, затем 122658: браузер отменит запрос A. |
| `track-500` (N06) | `GET /tracks/131672` сразу возвращает HTTP 500. |
| `track-timeout` (N06) | `GET /tracks/131672` отвечает через 9000 мс, то есть после 8-секундного тайм-аута frontend. |
| `drop-selected` (D11) | С 5-го тика из каждого полного снимка удаляются борт 131672 и его предупреждения; выберите его до 5-го тика. |
| `partial-alert`, `partial-status`, `partial-both` (N08) | На 3-м тике вместо полного снимка приходят только alert, только status или оба отдельных кадра; 4-й тик снова полный. |
| `slow-first` (FE-14) | При новом WS-подключении начальный снимок не отправляется; первые 5 периодических тиков также пропускаются, на 6-м приходит полный актуальный снимок. |
| `long-track` (FE-11) | Только `GET /tracks/131672` отдаёт 35 синтетических остановок от исходной первой до целевой последней; остальные маршруты и WS не меняются. |
| `status-skew` (P0-1) | На каждом периодическом тике `status.sim_time` позже `sim_time` кадра на 1–50 мс с микросекундами, как у реального backend. Кадры должны приниматься: счётчики и карта обновляются. |
| `rewind` (P0-2) | С 5-го тика все метки времени кадра сдвинуты на час назад без переподключения WS, как при `--loop` или `POST /api/v1/replay/control`. Ожидается новый сеанс: часы в шапке идут от раннего времени, статус «Поток подключён». |

`STUB_TR_ID` меняет целевой борт (по умолчанию `131672`), `STUB_TRIGGER_TICK` — тик WS-инъекции (по умолчанию 3; для `drop-selected`, `slow-first` и `rewind` — 5). В `slow-first` это число пропускаемых тиков: первый полный кадр придёт на следующем. `STUB_DELAY_MS` — REST-задержка (по умолчанию 3500 для N05 и 9000 для timeout). Например:

Для сценариев `track-*` используйте `STUB_VEHICLES=3` (или другой снимок, в котором есть выбранный `STUB_TR_ID` и маршрут для него); stub проверяет наличие обоих при запуске.

```powershell
$env:STUB_CASE = 'track-race'
$env:STUB_TR_ID = '131672'
npm run dev:stub
```

Для отдельного экземпляра stub можно задать `STUB_PORT`; стандартный Vite-прокси по-прежнему направлен на порт 8000. После проверки удалите установленные переменные окружения PowerShell перед обычным запуском.

```bash
docker build -t proact-frontend ./frontend
docker run --rm -p 3000:3000 proact-frontend
```

В контейнере демо (`/?source=demo`) работает и без backend. Для живого потока контейнер должен находиться в сети, где доступно имя `backend` (так в корневом `docker-compose.yml`).

## Данные и ограничения

Для географической карты нужен доступ браузера к `tiles.openfreemap.org`. Подложка использует тёмный стиль OpenFreeMap и данные OpenStreetMap; атрибуция отображается на карте. URL стиля задаётся через `VITE_MAP_STYLE_URL` (пример в [.env.example](.env.example)). Значение `offline` включает локальную резервную **схему без географической подложки и тайлов**; это не полноценная офлайн-карта. При недоступности стиля интерфейс переключается на эту схему. Ошибка отдельного тайла или шрифта не должна скрывать всю карту.

Демо-снимок содержит три борта из контрактного примера, а не весь транспорт Москвы. В режиме «Живой поток» frontend учитывает все борта, которые сервер передаёт в `vehicles` сообщения WebSocket; карта показывает только записи с допустимой позицией и отдельно объясняет разницу. Для плотного снимка близкие маркеры группируются, выбранный борт остаётся доступным отдельно. Если backend недоступен или передаёт неполный снимок, frontend не может восстановить отсутствующие борта из демо-данных. При отсутствии WebGL остаются список бортов, предупреждения и карточка.

Базовые формы данных следуют `contracts/schemas.py`, а исходный снимок скопирован из `contracts/examples/ws_snapshot.json`. TypeScript-валидатор дополнительно отвергает дубли `tr_id`/`alert_id`, вероятность вне 0–1, нарушенный порядок q10–q90 и нечисловые обязательные координаты, чтобы не показывать противоречивый кадр. Числовая широта вне географического диапазона остаётся в числе полученных бортов, но не создаёт маркер: Python-контракт не ограничивает её диапазон. Время сравнивается с точностью до микросекунд в московском локальном формате без таймзоны. Плановые остановки и треки для демо созданы специально для интерфейса: ID и времена исходного снимка расходятся с опубликованным расписанием. Времена фактических прибытий из train/test/validate не используются; наблюдения и факты позднее момента снимка `T` отсекаются при отображении маршрута.

Диаграмма показывает план, наблюдения и q10–q90 для выбранного борта или события. Расстояние наблюдения вычисляется проекцией координат на отрезки маршрута. Реальное качество прогнозов здесь не оценивается. Кнопка «Отправить водителю» вызывает `POST /api/v1/actions`; ответ водителя эмулирует backend, в демо — сам frontend. Истории решений в интерфейсе нет. Полный end-to-end с backend требует его доступного сервиса и совместимых ответов.
