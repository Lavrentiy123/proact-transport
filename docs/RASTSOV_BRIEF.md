### 3.1 Утечка в данных: что это и откуда 1.0 у других команд

Проверено на файлах (и совпадает с `DEEP_ANALYSIS_RESULT.md` §0, п. 1–3).

- `validate/schedule_plan.csv` и `test/schedule.csv` содержат **одни и те же 5 558 строк** расписания одного дня, 06.01.2026.
- Для **всех 151** целевых остановок validate точный факт прибытия `time_fact_begin` лежит в `test/schedule.csv` и в `train/schedule.csv`. В test совпадение с разметкой точное: `target_delay_s` = факт − план у 353 из 353 точек.
- `validate/traffic.csv` побайтно совпадает с `test/traffic.csv` (105 945 одинаковых пакетов). В нём есть телеметрия **после** T: у 98 % точек validate есть данные позже T+15 мин.

Отсюда два «математических» пути к скору 1.0:
- взять факт из `schedule.csv`;
- посмотреть, когда борт проехал остановку, по телеметрии после T.

**Оба нарушают правило** из `data/DATASET_README.md` §1: для точки T можно использовать только телеметрию с `event_time ≤ T` и подсказку `cur_dev_s`.

### 3.3 Наш код и наши сабмиты — утечки нет, но есть риск ложного подозрения

**Код.**
- В `src/train.py` (после `1cbc225`) признаки validate строятся из `validate/traffic.csv` и `validate/schedule_plan.csv`.
- Фильтр `event_time_dt <= t_moment` стоит в `src/feature_engineering.py:113`.
- Удалённый блок «Local ground truth check for validate» подтягивал факты из `test/schedule.csv`, но только **печатал** MAE, на прогноз он не влиял.
- `time_fact_begin` встречается только в `tests/` и `src/eda/`. Это охраняет `tests/ml/test_no_leakage_static.py`.
- `features/` режет окно `(T − 30 мин, T]`. Тест «полный трек = обрезанный = обрезанный + мусор после T» проходит (`reports/tasks/ML-T2.md`).
- Мой прогон: 33 из 34 быстрых тестов (единственный красный — `test_env`, у меня нет `catboost`) и 5 из 5 медленных, в том числе parity онлайн = офлайн.

**Сабмиты.** Я один раз сверил оба файла с фактами из `test/schedule.csv`, чтобы проверить, не восстановлены ли они из фактов:

| Файл | MAE против фактов |
|---|---|
| `submissions/sub_20260926_1352_baseline_v1.csv` | 56.7 с |
| старый `submission_catboost.csv` | 58.3 с |

Сабмит, собранный из фактов, дал бы MAE ≈ 0. **Значит, оба честные.** Скрипт сверки в репозиторий не добавлен. **Повторять эту сверку и выбирать по ней модели нельзя**: это и есть подглядывание в validate.

**Риск ложного подозрения.**
- Разбор оценивает порог шкалы как `MAE_TARGET ≈ 60 с` (`DEEP_ANALYSIS_RESULT.md` §I.3). Наш MAE ≈ 57 с ниже порога, так что **честная модель, скорее всего, покажет на платформе около 1.0**. Как у «математиков».
- Причина — устройство датасета: в train лежат синтетические копии тех же 13 бортов того же дня (корреляция 0.95–0.99, `DEEP_ANALYSIS_RESULT.md` §0 п. 2, §I.5). Честная оценка на новом борте (LOBO) — около 0.65.
- Отличить нас от «математиков» организаторы смогут только по потоку и по коду (#1937).

Следствие для плана: **критерий 1 (6 баллов) защищает не скор, а работающий ML на потоке.** Поток — это мой backend.

Что делать (решает капитан, ML-часть):
1. Написать организаторам **до** проверки, через модератора или поддержку, текст вопроса — в §9.2.
2. `docs/ANTI_LEAKAGE.md`. В нём: какие утечки мы нашли, почему не используем, как устроена валидация (LOBO), воспроизводимый `train.py`.
3. **Сабмит из потока.** Прогнать validate-день через `OnlineVehicle` (или через backend), взять прогнозы в моменты T из `validate/points.csv` и загрузить этот файл отдельным сабмитом. Тогда «подтверждение в потоковом режиме» у нас уже есть. Мой вклад — эндпоинт выгрузки журнала прогнозов, шаг 5 в §6.

### 5.3 Проверка на живом эмуляторе (сделано в этом разборе, одноразовый скрипт во временной папке)

Как проверял: `docker load -i data/ndtp-telemetry-emulator.tar` (образ `ndtp-telemetry-emulator:1.0`, amd64, Java 17, 134 МБ, готов через ~5 с после старта). Слушатель на `:9201`, конфиги через `POST /api/config`.

| Проверка | Результат |
|---|---|
| Кадры по спецификации | handshake: NPH `(0, 100)`, тело 18 байт `<HHHIII>` = (6, 2, 0, unitId, 65535, 0); realtime: NPH `(1, 101)` |
| Состав realtime при `autoGenerate` | ячейки 0, 8, 16, 2, 10; тело 123 байта, разбирается целиком |
| **CRC** | CRC-16/Modbus по NPH + телу. Прочитанное как u16 LE поле NPL = **байт-свап** CRC. Сошлось 26 из 26 и 5 из 5 кадров. Парсеру нужно сравнивать `crc_field == swap(crc)` |
| `timestamp` в Nav00 | **Всегда текущее время.** Исторического времени эмулятор не передаёт |
| Каждый `POST /api/config` | **Рвёт все TCP-сессии** и открывает новые с handshake |
| Явные координаты, плоские поля (как в спецификации и в разборе) | Эмулятор отвечает `"fields":{}` и поле пропадает |
| Явные координаты, формат `{"type":"G6CellNav00","fields":{...}}` | Координаты, скорость и курс приходят точно |
| Невалидный конфиг (дубль `unitId`) | HTTP 400 с понятным `message` |

Следствия:
- Парсер из разбора годится с одной правкой: сравнение CRC.
- Replay через эмулятор (пере-POST каждого фикса) возможен только с форматом `fields` и с реконнектом на каждом POST, поэтому это P1.
- Наш собственный replay-клиент остаётся основным.

## 8. Git: ветки, слияния, конфликты

### 8.1 Можно ли работать в своей ветке независимо

Да. Мои папки: `backend/`, `docker-compose.yml`, `docs/perf.md`, `docs/JURY_GUIDE.md`, `tests/backend/`, `scripts/`. Они ни с кем не пересекаются.

| Точка связи | С кем | Что может сломаться | Защита |
|---|---|---|---|
| `features/` (`OnlineVehicle`, `load_schedule`, `features_to_json`) | капитан | ML-T3 или ML-T5 меняют сигнатуры или `FEATURE_NAMES` | тест `tests/backend/test_features_contract.py` (`push / target_at / features_at / derived`); прогон после каждого `git merge origin/main` |
| `contracts/schemas.py` | капитан (владелец), Пуртов | переименование полей | меняю только через капитана; новые необязательные поля добавлять можно (`contracts/README.md`) |
| `ml-core /v1/predict` | капитан | появится только к 22:00 | fallback внутри backend; клиент строго по `PredictRequest` / `PredictResponse` |
| REST и WS для фронта | Пуртов | фронт ждёт поле, которого нет | заглушки по контракту к 17:00, дальше настоящие данные той же формы |

| `.gitignore`, `requirements*` | все | мелкие конфликты | свои зависимости — `backend/requirements.txt` |

### 8.2 Как часто сливать

- `git fetch origin && git merge origin/main` к себе — после каждого пуша капитана, минимум раз в 2 ч. **Только merge, без rebase и без `push --force`.**
- Свой пуш — после каждого шага плана.
- В `main` — только на контрольных точках 22:00, 14:00, 18:00 (TEAM_PLAN §6).

### 8.3 Безопасный порядок слияния на контрольной точке

1. Я вливаю `origin/main` в `rastsov/backend`, прогоняю `pytest tests/backend tests/ml -m "not slow"` и smoke, пушу.
2. `main` ← `rastsov/backend` (`--no-ff`). Backend идёт первым: compose и API мои, фронт от них зависит.
3. Пуртов вливает `origin/main` к себе, проверяет дашборд на настоящем API, пушит.
4. `main` ← `purtov/frontend` (`--no-ff`).
5. Smoke с нуля на `main`: `git clone` → `docker compose up --build`.

Конфликт в чужой папке не решаем за владельца, пишем ему (так же в промте капитана, ML-T7).
