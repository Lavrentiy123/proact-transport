ПРАВИЛО ANTI-LEAKAGE (Честность модели):
При прогнозе для точки (tr_id, T) строго запрещено использовать любые данные телеметрии с event_time > T. Любой взгляд в будущее дисквалифицирует решение!

МЕТРИКА ОЦЕНИВАНИЯ В DATA SCIENCE:
- MAE = mean(|факт - прогноз|) в секундах.
- mae_zero = mean(|факт|) (ошибка константного прогноза 0).
- score = max(0, min(1, (mae_zero - MAE) / (mae_zero - MAE_TARGET))) in [0, 1].
- Бейзлайн (прогноз = cur_dev_s) дает score ≈ 0.40 (MAE ≈ 88-93 с).
- Целевой score для 6 из 6 баллов: score >= 0.70 (требуется MAE <= 65-70 с).

### РАЗДЕЛ I: ГЛУБОКИЙ АНАЛИЗ ДАННЫХ И ML-МАТЕМАТИКА
1. Вход и выход модели:
   - Математическая постановка задачи: почему прогнозирование дельты задержки Δ = (target_delay_s - cur_dev_s) на порядок эффективнее прогнозирования сырого target_delay_s?
   - Физический смысл целевой переменной, анализ асимметрии штрафов (опоздание опаснее нагона для интервала).
2. Feature Engineering (строгий anti-leakage t <= T):
   - Детальный список признаков в 5 категориях:
     а) Временные и суточные циклы (часы пик Москвы);
     б) Пространственно-геометрические (дистанция Гаверсинуса до целевой остановки, координаты, курс);
     в) Кинематические и телематические за окна 1, 3, 5, 10 минут (скорость, ускорение, доля времени в стоянии speed < 2 км/ч, турбулентность скорости);
     г) Сетевые и расписания (число промежуточных остановок между T и целевой, требуемая скорость прибытия V_req = Distance / Horizon, расхождение скоростей);
     д) Межбортовые (headway до лидера, скорость впереди идущего на том же перегоне).
3. Архитектура ML-ядра:
   - Стек: CatBoostRegressor (с функцией потерь MAE / Huber) + LightGBM / PyTorch (для временных последовательностей).
   - Стратегия валидации: строгий TimeSeriesSplit / Purged Group Split (без заглядывания во времени).
   - Оптимизация инференса: квантование и экспорт в ONNX Runtime (обеспечение latency < 5 мс).
   - Модуль объяснимости (Explainable AI): извлечение SHAP values в реальном времени для формирования причины сбоя (задержка посадки, затор на перегоне, снижение скорости).

### РАЗДЕЛ II: BACKEND И ПОТОКОВАЯ АРХИТЕКТУРА (HIGH-LOAD & RESILIENCE)
1. Компонентная структура Backend-сервиса (Python 3.12 + FastAPI + asyncio):
   - NDTP Ingestion Service: асинхронный консьюмер TCP-сокетов от эмулятора ndtp-telemetry-emulator (порт 18080) и фоллбек на Replay-воркер исторических CSV.
   - Circular Memory Buffer: потоковое скользящее окно последних координат бортов для расчета скоростей за 1-3-5 минут без блокировок БД.
   - Schedule & Topology Cache: быстрая пространственная привязка (R-Tree / KD-Tree / Shapely).
   - Inference Orchestrator: батчевый запуск модели каждые N секунд.
   - СППР (Система Поддержки Принятия Решений): алгоритм Dynamic Holding (расчет секунд удержания заднего борта на узловой остановке t_hold = clip(alpha * (H_target - H_pred), 0, 90) для предотвращения Bus Bunching).
2. API Контракты (REST + WebSocket):
   - Проектирование Pydantic v2 схем и эндпоинтов:
     * GET /api/v1/vehicles — текущие координаты, скорости и задержки всех ТС;
     * GET /api/v1/alerts — список критических инцидентов с горизонтом 10–15 минут, вероятностью, причиной и рекомендацией;
     * POST /api/v1/what-if/simulate — эмуляция воздействия удержания или ввода резерва с пересчетом графика;
     * POST /api/v1/actions/apply — аудит-лог принятия решения диспетчером;
     * WebSocket /ws/live — потоковый пуш телеметрии и алертов на фронтенд с частотой 1 Гц.
3. Отказоустойчивость и Graceful Degradation (под Критерий 5):
   - Что делать при внезапном разрыве TCP-коннекта с эмулятором телематики? (Heartbeat, перевод в режим экстраполяции по расписанию и последней скорости, уведомление фронтенда о переходе в автономный режим, автоматический реконнект без падения сервиса).
   - Защита от накопления очередей (backpressure и отбрасывание устаревших кадров телеметрии).
