# Текст для формы «Загрузка решения»: производительность и дополнительные возможности (П6, П8)

Все числа получены командами из [`docs/perf.md`](perf.md) на ноутбуке команды (8 ядер, 32 ГБ, Docker Desktop, Windows 11).

## Производительность и надёжность (текст в поле формы)

- Холодный старт: от `docker compose up -d` до готовности API (`/ready`) — 12.8 с, до первого прогноза в API (`/api/v1/vehicles`) — 15.0 с. Первая сборка образов без кэша Docker — 121 с.
- Тик прогнозов (13 бортов с расписанием, признаки + вызов ml-core + алерты): p50 13.1 мс, p99 24.9 мс при периоде тика 5 с времени симуляции (при replay ×10 — 0.5 с реального времени); перегрузок тика — 0.
- Вызов ml-core на батч тика (HTTP, ансамбль CatBoost + PyTorch/ONNX, квантили, причины): p50 49.5 мс, p99 151.7 мс на загруженном ноутбуке, текущие модели (прежний ансамбль без CatBoost m_online — 27.9 / 123.7 мс, один CatBoost — 7.6 / 13.5 мс); тик p50 105 мс, p99 290 мс при периоде 500 мс; таймаут клиента ml-core 1 с (`docs/perf.md`, `reports/logs/perf_load_v2_detector.jsonl`).
- Приём NDTP: парсер разбирает 110 851 кадров/с в одном потоке (9.0 мкс на кадр); на потоке replay ×10 — 13.9 пакетов/с без ошибок CRC; нагрузка официальным эмулятором 1000 юнитов × 1 пакет/с — 1013.7 пакетов/с, тик p99 26.9 мс.
- Ответ REST `GET /api/v1/vehicles`: p50 23.2 мс, p99 47.0 мс; WebSocket — снапшот раз в 1.0 с, 8 049 байт.
- Надёжность (скрипт `scripts/chaos.sh`): обрыв потока → режим DEGRADED через 14.7 с после остановки источника (15.6 с от начала команды остановки; порог — 15 с без пакетов), прогнозы продолжаются по расписанию (`quality=fallback`), сервис отвечает; поток вернулся → LIVE через 1.8 с; падение ml-core → прогноз по правилу через 0.2 с, возврат ml-core через 31.3 с (circuit breaker).
- Горизонт: 100 % прогнозов выданы за 10–15 минут до планового прибытия (`/api/v1/metrics/horizon`, `share_lead_in_window = 1.0`); онлайн-MAE на живом потоке (docker compose, NDTP, текущие модели на детекторе v2) — 85.2 с против 134.0 с у бейзлайна «задержка = текущее отклонение» на 6 743 сверенных прогнозах (прежние модели: 88.8 против 150.6 с).
- ML-ядро: признаки одного борта по 30-минутному буферу — 2 мс; `/v1/predict` на 30 бортов вместе с ансамблем (CatBoost + PyTorch/ONNX), интервалом q10–q90 и причинами — ~27 мс в покое (37.5 мс под нагрузкой ноутбука); член ансамбля PyTorch в ONNX — 0.8 мс на батч 30; холодный старт контейнера ml-core до `/ready` — 14 с (`models/model_card.json`, `tests/ml_core/test_api.py`).
- Точность: скор на сайте 1.00 (верх шкалы) с первой попытки; сабмит — MAE 63.0 с на тесте организаторов против 93.4 с у бейзлайна; честная оценка на незнакомом борту (LOBO) — 75.2 с (модели на детекторе v2 — 74.6 с); на потоке для незнакомого борта — 83.8 с против 128.5 с у бейзлайна по восстановленному отклонению и 103.3 с у прогноза «0»; сабмит из потока (validate-день через ту же цепочку, что backend, без подсказки организаторов) — official 68.8 с, оценка скора ≈ 0.82 (`docs/model_card.md`).

## Дополнительные возможности (список для формы)

1. Настоящий бинарный NDTP по TCP: парсер и CRC-16/Modbus проверены на живом образе организаторов (20 реальных кадров в тестах), ресинхронизация после мусора, счётчики ошибок.
2. Replay реального дня по NDTP с сохранением реального порядка и задержек доставки пакетов (`receive_time`), управление скоростью и моментом старта через API; по концу дня replay сам перематывает время на старт — стенд работает сутками без ручных действий.
3. Управление официальным эмулятором из backend: автоматическая настройка через REST, сторожок после перезапуска эмулятора, режим реальных треков датасета через эмулятор, нагрузочный режим на 1000 юнитов.
4. Прогноз строго в окне 10–15 минут по построению, журнал всех прогнозов со сверкой по фактическому прибытию, которое увидел поток, выгрузка журнала в CSV в формате `sample_id` датасета.
5. Причина задержки с числовым доказательством из буфера телеметрии (затор, стоянка, накопленное отставание, тяжёлый участок, опережение, мало данных) и рекомендации диспетчеру по правилам: скорость до остановки, межрейсовая стоянка, резерв на первом/последнем рейсе.
6. Алерты с гистерезисом (не мигают при сдвиге окна), решения диспетчера (`apply/dismiss`) с журналом аудита и эмуляцией ответа водителя.
7. Graceful degradation: режим DEGRADED с прогнозом по расписанию, stale-борта, circuit breaker ml-core с прогнозом по правилу, отбрасывание пакетов «из будущего».
8. Метрики Prometheus (`/metrics`): пакеты, CRC, тик и инференс p50/p99, отброшенные пакеты, онлайн-MAE, доля горизонта.
9. Swagger (`/docs`) и документация по коду pdoc (`docs/api/backend`, `docs/api/ml`), chaos-тест одной командой.
10. Ансамбль моделей: CatBoost по табличным признакам + PyTorch MLP, экспорт в ONNX и инференс через onnxruntime без torch в образе; веса членов выбраны честной валидацией по бортам (CatBoost 0.2 + CatBoost по расписанию 0.5 + PyTorch 0.3); проверено int8-квантование ONNX (оставлен fp32: квантование меняло прогноз на ~7 с без выигрыша в скорости).
11. Один пакет признаков для обучения и потока: 34 признака, совпадение онлайн/офлайн до 1e-6 (тест), детектор прибытий на остановки (привязка GPS к плановым остановкам с монотонным указателем, окном по текущему отклонению, отправлением на конечных и проверкой направления движения против проезда по встречной) — восстанавливает текущее отклонение на потоке; версия v2 сократила ошибку восстановленного отклонения как прогноза со 162 до 128 с на незнакомом борту.
12. Вероятностный прогноз: интервал q10–q90 (квантильные CatBoost, ширина откалибрована до 80 % на незнакомых бортах) и P(опоздание > 120 с) для цвета риска.
13. Объяснимость: причина задержки через групповую окклюзию признаков (вклад групп «затор», «посадка», «накопленное отставание», «сложный участок» в секундах).
14. Честная валидация и анти-утечка: оценка на отложенном борту вместе с его синтетическими копиями (LOBO) и сдвигом во времени; найденная утечка (validate — тот же период, что test) не использована; статические и динамические тесты анти-утечки (`docs/ANTI_LEAKAGE.md`).
15. Оценка бизнес-эффекта: калькулятор избыточного ожидания пассажиров (EWT) и демо на данных дня — межрейсовая стоянка ≤ 60 с сокращает ожидание на 0.79 мин на пассажира (`docs/business_effect.md`).
16. What-If на дашборде: в карточке алерта ползунок средней скорости до целевой остановки пересчитывает отклонение и время прибытия (дистанция — из рекомендации backend, при скорости из прогноза модели оценка совпадает с прогнозом).
17. Дашборд живого потока: сеть маршрутов всех бортов с цветом риска поверх тёмной подложки OpenFreeMap (данные OpenStreetMap; схема видна и без интернета), целевая остановка и участок «откуда → куда», панель «доля прогнозов за 10–15 мин и онлайн-ошибка», обрыв потока (плашка «ДЕГРАДАЦИЯ») и отказ ML-ядра видны баннерами, решения диспетчера в один клик.
